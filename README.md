# MeetupBoard — афиша IT-митапов

REST API афиши IT-мероприятий. Организаторы публикуют митапы и конференции с датой, городом или
онлайн-форматом и лимитом мест, участники записываются, обсуждают программу и подписываются на
организаторов — лента показывает их новые мероприятия.

**Стек:** Python 3.12 · Django 5.2 · Django Ninja · jwtninja 2 (JWT с серверными сессиями) ·
Pydantic v2 · PostgreSQL (SQLite для разработки) · python-slugify · Hurl · ruff · ty + django-stubs ·
Docker · GitHub Actions.

## Референс и что из него взято

Проект — переделка [c4ffein/realworld-django-ninja](https://github.com/c4ffein/realworld-django-ninja),
эталонной реализации спецификации RealWorld для Django Ninja (сам референс — порт DRF-проекта
Sean-Miningah на Ninja). Технология и архитектура сохранены, предметная область заменена:
статьи → мероприятия, избранное → регистрация на мероприятие с лимитом мест, комментарии →
обсуждение, подписки на авторов → подписки на организаторов.

| Приём референса | Как реализован здесь |
|---|---|
| Один `NinjaAPI`: роутеры приложений под `/api`, роутер jwtninja под `/auth` | `config/urls.py` |
| Обработчики исключений `NinjaAPI`, приводящие ошибки к формату `{"errors": {…}}` | `config/urls.py` + обработчик `APIError` jwtninja |
| `TokenAuth`: префиксы `Token` и `Bearer`, режим `pass_even` для анонимного доступа | `helpers/jwt_utils.py` — теперь наследник `JWTAuth` из jwtninja |
| `ModelSchema` + `Field(alias=…)` для camelCase, `resolve_*` для вычисляемых полей | `apps/*/schemas.py` |
| Маркер `EMPTY`: «поле не передано» ≠ `None` (PUT работает как PATCH, как требует спецификация) | `helpers/empty.py` |
| `get_or_404(model_or_qs, "<ресурс>", …)` — имя ресурса в тексте 404 | `helpers/exceptions.py` |
| Аннотации QuerySet вместо запроса на каждую запись (`with_favorites`) | `EventQuerySet.with_attendance`: число участников, «я иду», «я подписан на организатора» |
| Флаг «подписан на автора комментария» — аннотацией | `apps/comments/api.py` |
| Тесты на `django.test` + `parameterized`, Hurl-сценарии, Makefile с `make verify`, `CLAUDE.md` для ИИ-агента | `apps/*/tests.py`, `tests/hurl/`, `Makefile`, `CLAUDE.md` |

## Что исправлено по сравнению с референсом

1. **Аутентификация повторяла jwtninja не полностью.** `TokenAuth` референса — собственная копия
   `authenticate`, в которой нет трёх проверок оригинала: типа токена (refresh-токен из `/auth/login/`
   принимался как access), принадлежности сессии пользователю из токена и security stamp (после смены
   пароля старые токены продолжали работать). Здесь `TokenAuth` наследует `JWTAuth` и получает все
   проверки — тесты `test_refresh_token_is_not_accepted_as_access_token` и
   `test_password_change_revokes_old_tokens`.
2. **Версия jwtninja не закреплена, а настройки — от 1.x.** В зависимостях просто `jwtninja`, в
   настройках — словарь `JWT_NINJA`. Актуальная 2.x требует отдельный `JWT_SECRET_KEY` (для HS256 — не
   короче 32 байт), `JWT_ISSUER` и `JWT_AUDIENCE`, иначе `ImproperlyConfigured`. Кроме того, `APIError`
   в 2.x не наследует `HttpError`, и обработчики референса его не ловят. Здесь настройки 2.x (секреты —
   из окружения) и отдельный обработчик `APIError`: для `/api` — `{"errors": {"token": ["invalid_token"]}}`
   со статусом 401, для `/auth` — документированный формат jwtninja.
3. **Новая серверная сессия на каждый `GET /user`.** Референс выпускал новый токен при каждом запросе
   текущего пользователя. В jwtninja 2 действует лимит активных сессий (`MAX_ACTIVE_SESSIONS`, по
   умолчанию 20), и при превышении самые старые принудительно истекают: после двадцатого `GET /user`
   переставал работать токен, с которым клиент вошёл. Здесь `GET /user` возвращает текущий токен,
   тест проверяет, что число сессий не растёт.
4. **Конфликт в `PUT /user` → 500.** Смена email или username на занятый падала с `IntegrityError`,
   который никто не перехватывал. Здесь — 409 с указанием поля.
5. **Email с учётом регистра.** Менеджер пользователей не нормализовал email: `Anna@Example.com` и
   `anna@example.com` регистрировались как два аккаунта, а вход зависел от регистра. Здесь email
   приводится к нижнему регистру и проверяется через `iexact`.
6. **Флаги в списке всегда `false`.** `GET /articles` объявлен без `auth`, поэтому для клиента с JWT
   `request.user` оставался анонимным, и `favorited` / `following` в списке не отражали пользователя.
   Здесь список работает через `TokenAuth(pass_even=True)`, тест проверяет флаг `attending` в списке.
7. **N+1 в списке.** Теги (`obj.tags.all()` в резолвере) и автор (внешний ключ без `select_related`)
   загружались отдельным запросом на каждую статью. Здесь `select_related` + `prefetch_related` +
   аннотации, а тест `test_list_has_no_n_plus_one` ограничивает страницу из 10 мероприятий пятью запросами.
8. **Пагинация без проверок.** Отрицательный `offset` приводил к `ValueError` в срезе QuerySet (500),
   `limit` не ограничивался. Здесь — 422 для неверных значений и потолок `limit` = 100.
9. **Кириллица в slug.** `django.utils.text.slugify` без `allow_unicode` выбрасывает русские буквы:
   заголовок из одних кириллических слов давал пустой slug. Здесь `python-slugify` с транслитерацией:
   «Встреча Python-разработчиков» → `vstrecha-python-razrabotchikov`.
10. **Теги создавались вне транзакции** — ещё до создания статьи, поэтому при отказе они оставались
    в базе. Здесь теги создаются в одной транзакции с мероприятием.
11. **Комментарий искался по id без привязки к статье из URL:** удаление через
    `/articles/<любой slug>/comments/<id>` срабатывало и для комментария другой статьи. Здесь комментарий
    ищется в пределах мероприятия, иначе — 404.
12. **Проверка типов с отключёнными правилами.** В референсе ty 0.0.1a7 и три правила выключены из-за
    динамики Django. Здесь включены все правила ty: типы Django даёт django-stubs, менеджер `EventManager`
    объявлен явно, поля из аннотаций описаны в моделях.

Мелочи: повторная подписка отвечала 409 с пустым телом (теперь — с сообщением), `SECRET_KEY` был
записан прямо в `settings.py` (теперь читается из окружения).

## Предметная область

- **Мероприятие:** заголовок, краткое описание, программа, дата и время начала (только в будущем),
  город, онлайн-формат, площадка, вместимость (от 1 до 100 000 или без ограничения), до 10 тегов
  (регистр и дубли нормализуются).
- **Запись на мероприятие:** `POST /events/{slug}/attend` блокирует строку мероприятия
  (`SELECT … FOR UPDATE`), поэтому два участника не займут одно последнее место одновременно.
  На прошедшее мероприятие записаться нельзя (400), при нехватке мест или повторной записи — 409.
  В ответе — `attendeesCount`, `seatsLeft`, `attending`.
- **Организатор** меняет и удаляет только свои мероприятия; вместимость нельзя уменьшить ниже числа
  уже записавшихся (409).
- **Фильтры списка:** `tag`, `organizer`, `attendee`, `city` (по подстроке), `online`, `upcoming`
  (только будущие, по дате начала), `limit`, `offset`.
- **Обсуждения:** удалить комментарий может его автор или организатор мероприятия.

## API

Документация OpenAPI (Swagger UI) — `/docs`. Авторизация: `Authorization: Token <jwt>`
(как в спецификации RealWorld) или `Authorization: Bearer <jwt>`.

| Метод | Путь | Доступ | Назначение |
|---|---|---|---|
| POST | `/api/users` | все | Регистрация, выдаёт JWT |
| POST | `/api/users/login` | все | Вход |
| GET / PUT | `/api/user` | авторизованные | Текущий пользователь / частичное обновление |
| GET | `/api/profiles/{username}` | все | Профиль |
| POST / DELETE | `/api/profiles/{username}/follow` | авторизованные | Подписаться на организатора / отписаться |
| GET | `/api/events` | все | Список с фильтрами и пагинацией |
| GET | `/api/events/feed` | авторизованные | Мероприятия организаторов из подписок |
| POST | `/api/events` | авторизованные | Создать мероприятие |
| GET / PUT / DELETE | `/api/events/{slug}` | все / организатор / организатор | Получить / изменить / удалить |
| POST / DELETE | `/api/events/{slug}/attend` | авторизованные | Записаться / отменить запись |
| GET / POST | `/api/events/{slug}/comments` | все / авторизованные | Обсуждение |
| DELETE | `/api/events/{slug}/comments/{id}` | автор или организатор | Удалить комментарий |
| GET | `/api/tags` | все | Все теги |
| — | `/auth/…` | — | Эндпоинты jwtninja: вход с refresh-токеном, обновление токена, список сессий |

Пример запроса:

```bash
curl -X POST http://localhost:8002/api/events \
  -H "Authorization: Token <jwt>" -H "Content-Type: application/json" \
  -d '{"event": {"title": "Python-митап: асинхронность", "description": "Три доклада и нетворкинг",
       "body": "19:00 — сбор гостей, 19:30 — доклады", "startsAt": "2027-03-14T19:00:00+03:00",
       "city": "Казань", "venue": "Коворкинг «Точка»", "capacity": 80, "tagList": ["python", "asyncio"]}}'
```

## Быстрый старт

### Docker

```bash
docker compose up --build        # API и PostgreSQL; документация — http://localhost:8002/docs
```

### Локально

```bash
uv sync --group dev
uv run python manage.py migrate      # без DATABASE_URL используется SQLite
uv run python manage.py runserver    # http://localhost:8000/docs
```

Переменные окружения перечислены в `.env.example`.

## Тесты и качество кода

```bash
make verify                          # ruff + ty + быстрые тесты (SQLite в памяти)
make test                            # тесты с покрытием, порог 95 %
DATABASE_URL=postgres://postgres:postgres@localhost:5432/meetups make test   # на PostgreSQL
make test-hurl-with-managed-server   # Hurl-сценарии: сервер поднимается и останавливается сам
```

57 тестов проходят на SQLite и PostgreSQL, покрытие — 98 %. Hurl-сценарий из 13 запросов проходит
путь пользователя целиком через HTTP. В CI четыре пайплайна: тесты (матрица SQLite / PostgreSQL),
линтер, типы и Hurl.

## Структура

```
config/              # настройки из окружения; urls: NinjaAPI, роутеры, обработчики ошибок
apps/
├── accounts/        # User, регистрация и вход, текущий пользователь, профили, подписки
├── events/          # мероприятия, теги, запись участников, фильтры, лента
└── comments/        # обсуждения мероприятий
helpers/             # TokenAuth и выпуск JWT, get_or_404, маркер EMPTY, базовый класс API-тестов
tests/hurl/          # сквозные сценарии Hurl
CLAUDE.md            # инструкции для ИИ-агента: команды, архитектура, соглашения
```
